# 2026-11-03 — 修周更编排脚本单源卡死（不发版）

## 现象

`crawl-weekly` 的 run `41473298641` 从 2026-11-02T15:36:46Z 起一直 `in_progress`，
P2 步骤挂了 20+ 小时没结束。job 级的 `timeout-minutes: 30` 没有把它截断，
而 `concurrency.cancel-in-progress: false` 又让后续 dispatch 一直 `pending`。
结果是整个周更队列被一个卡死的源站堵住，数据停止更新。

## 根因

`scripts/run_weekly_source_group.py` 用 `for line in process.stdout` 流式读取子进程输出：

- 子进程（抓取脚本）里的 `requests` 没有整体超时，某个源站 socket 半开时会永久阻塞；
- 读取方没有任何墙钟上限，子进程不退出，编排器就永远等下去；
- 编排器不退，job 就一直占着 concurrency 组。

也就是说：**单个来源卡死 = 整条周更永久停摆**，而且没有告警。

## 改动

- `scripts/run_weekly_source_group.py`
  - 新增 `_source_timeout_seconds()`：单源墙钟上限默认 420s，可用环境变量
    `WEEKLY_SOURCE_TIMEOUT_SECONDS` 覆盖。
  - 读日志改为「后台线程泵 + `queue.get(timeout=...)`」，到点 `process.kill()`；
    超时来源记为 `STATUS_TIMEOUT=124`（与 GNU `timeout` 约定一致），归入「来源失败」
    而不是「编排失败」，因此 P2 超时只告警、不会拖垮整组。
  - 超时发专用的 `::warning|error title=<组> 周更来源超时::` annotation，
    日志落 `[orchestration-error] 超时 Ns 未结束，已 kill`，job summary 状态显示「超时」。
  - 把 `process.stdout` 在启动线程前绑定到局部变量，避免线程延迟启动时
    串读到下一个来源的管道。
- `scripts/run_weekly_source_group.py`（第二处）
  - 实测同一轮 P1 里 `sz-education` / `sz-planned-supply` / `sz-affordable-projects`
    三个源都因 `Connection reset by peer` 失败，导致整周变红。P1/P2 首轮失败的来源
    现在会在整组跑完后各重试一次（间隔 2s），成功则恢复绿色并输出
    `::notice P1 周更重试成功`；超时与编排失败不重试。最终 status/summary 写的是
    重试后的结论，日志分 `p1-<源>.log` 与 `p1-<源>-retry.log` 两份。
- `scripts/git_push_retry.sh`（第三处）
  - 线上实测：并发排队时两个 run 都会重写 `static/seed/crawl_meta.json`，
    `git pull --rebase` 必然在这个文件上冲突，脚本连续 4 次 abort 后放弃，
    P0 提交步骤失败 → 整条 run 红（run `41479381303`，
    `CONFLICT (content): Merge conflict in realty_app/static/seed/crawl_meta.json`）。
  - 现在检测到 rebase 冲突时，用 `git checkout REBASE_HEAD -- <file>` 保留本次
    刚生成的数据（而不是上游旧版本），继续 rebase 后再 push；只处理内容冲突，
    删除/重命名等其它冲突仍照旧 abort。
- `scripts/crawl_lianjia_listings.py`（第四处，P0 主数据源）
  - 线上 run `41485761045` 的 P0 日志：深圳 30 条抓取成功，随后
    `AttributeError: 'int' object has no attribute 'strip'`，**整城数据写盘失败**，
    三个城市全部只打 WARN 后跳过 —— 也就是说挂牌数据已经静默停更。
    根因是 `cmd_fetch` 给新行赋的是 int 型 `listing_id`，而 `write_csv` 里用
    `(r.get("listing_id") or "").strip()` 校验。
  - 修复：校验前统一 `str()` 转换；本地真实跑
    `fetch --city 深圳 --pages 1 --append` 验证 1744 → 1774 行、exit 0。
  - 另外实测 `pg2` 起链家返回 `<title>CAPTCHA</title>`（本地和 runner 都一样），
    继续翻 10 页只是加重风控。现在第一页命中 CAPTCHA 就停止该城后续分页，
    不再空转 9 次请求。
- `.github/workflows/crawl-weekly.yml`
  - P1 step `timeout-minutes: 30`、P2 step `timeout-minutes: 18`：组内超时是第一道闸，
    step 级超时是硬上限（runner 层的 step 超时一定能生效，不依赖脚本自身）。
  - job `timeout-minutes` 30 → 90：P0(~10min) + P1 + 重试 + P2 + 两次提交在 30 分钟里
    太紧（实测 30 分钟到点被取消，P2 明明已成功却整条 run 仍 cancelled），
    而真正的防挂死已经下沉到 step 级。
- `tests/ciWorkflowContracts.test.ts`
  - `runFakeGroup` 支持注入额外 env；新增用例：P2 放一个 sleep 5s 的假来源，
    `WEEKLY_SOURCE_TIMEOUT_SECONDS=1` 时应被 kill、后续来源继续执行、
    status 为 `slow-source\t124`、有 `P2 周更来源超时` warning、summary 显示「超时」。
  - 新增用例：P1 假来源首轮 exit 7、第二轮恢复 exit 0 时，整组 exit 0、
    status 写重试后的 `0`、有两份日志、有「重试成功」notice。
  - 既有 P1/P2 失败用例的 trace 断言补上重试那一行（失败结论保持不变）。

## 取舍

- 420s 是「单源」上限，23 个 P1 源全部超时理论上仍会超过 30 分钟的 step 上限；
  那种情况说明环境整体不可用，step 超时让它显式失败正是期望行为。
- 重试只在整组跑完后做一次，不做无限重试；连续两轮都失败说明源站真的不可用，
  这时整周变红是应该的（并且会带具体的尾部日志 annotation）。
- 重试成功时首轮那条 `::error` annotation 仍留在 run 里（run 结论是绿色），
  这是刻意保留的现场证据：能看出当天确实抖动过一次。
- 只 kill 直接子进程（Python 抓取脚本自身），不保证清理孙进程；抓取脚本都不 fork，
  当前够用。
- 超时归入「来源失败」而非「编排失败」，是为了保持既有语义：P2 单源超时不应
  让 P2 整步 outcome=failure。
- 本次属于 CI/脚本改动，按 `docs/VERSIONING.md` 不 bump 版本。
