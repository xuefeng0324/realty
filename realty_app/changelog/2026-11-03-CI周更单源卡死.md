# 2026-11-03 — 修周更编排脚本单源卡死（不发版）

## 现象

`crawl-weekly` 的 run `41473298641` 从 2026-11-02T15:36:46Z 起一直 `in_progress`，
P2 步骤挂了 20+ 小时没结束。job 级的 `timeout-minutes: 30` 没有把它截断，
而 `concurrency.cancel-in-progress: false` 又让后续 dispatch 一直 `pending`。
结果是整个周更队列被一个卡死的源站堵住，数据停止更新。

## 根因

`scripts/run_weekly_source_group.py` 用 `for line in process.stdout` 流式读取子进程输出：

- 子进程（抓取脚本）里的 `requests` 没有整体超时，某个源站 socket 半开时会永久阻塞；
- 读取方没有任何墙钟上限，子进程不退出，编排器就永远等下去；
- 编排器不退，job 就一直占着 concurrency 组。

也就是说：**单个来源卡死 = 整条周更永久停摆**，而且没有告警。

## 改动

- `scripts/run_weekly_source_group.py`
  - 新增 `_source_timeout_seconds()`：单源墙钟上限默认 420s，可用环境变量
    `WEEKLY_SOURCE_TIMEOUT_SECONDS` 覆盖。
  - 读日志改为「后台线程泵 + `queue.get(timeout=...)`」，到点 `process.kill()`；
    超时来源记为 `STATUS_TIMEOUT=124`（与 GNU `timeout` 约定一致），归入「来源失败」
    而不是「编排失败」，因此 P2 超时只告警、不会拖垮整组。
  - 超时发专用的 `::warning|error title=<组> 周更来源超时::` annotation，
    日志落 `[orchestration-error] 超时 Ns 未结束，已 kill`，job summary 状态显示「超时」。
  - 把 `process.stdout` 在启动线程前绑定到局部变量，避免线程延迟启动时
    串读到下一个来源的管道。
- `.github/workflows/crawl-weekly.yml`
  - P1 step `timeout-minutes: 20`、P2 step `timeout-minutes: 12`：组内超时是第一道闸，
    step 级超时是硬上限（runner 层的 step 超时一定能生效，不依赖脚本自身）。
  - job `timeout-minutes` 30 → 60：P0(~10min) + P1 + P2 + 两次提交在 30 分钟里太紧，
    而真正的防挂死已经下沉到 step 级。
- `tests/ciWorkflowContracts.test.ts`
  - `runFakeGroup` 支持注入额外 env；新增用例：P2 放一个 sleep 5s 的假来源，
    `WEEKLY_SOURCE_TIMEOUT_SECONDS=1` 时应被 kill、后续来源继续执行、
    status 为 `slow-source\t124`、有 `P2 周更来源超时` warning、summary 显示「超时」。

## 验证

- `python -m py_compile scripts/run_weekly_source_group.py` ✅
- `npx vitest run tests/ciWorkflowContracts.test.ts` ✅ 11/11（含新增超时用例，
  真实起子进程、真实 kill，1172ms 跑完）
- `npm run type-check` ✅
- `npm test` ✅ 154 文件 / 1448 用例全绿

## 取舍

- 420s 是「单源」上限，23 个 P1 源全部超时理论上仍会超过 20 分钟的 step 上限；
  那种情况说明环境整体不可用，step 超时让它显式失败正是期望行为。
- 只 kill 直接子进程（Python 抓取脚本自身），不保证清理孙进程；抓取脚本都不 fork，
  当前够用。
- 超时归入「来源失败」而非「编排失败」，是为了保持既有语义：P2 单源超时不应
  让 P2 整步 outcome=failure。
- 本次属于 CI/脚本改动，按 `docs/VERSIONING.md` 不 bump 版本。
