## 修了什么 bug

### 背景

`crawl_sz_land_deals.py` 和 `crawl_sz_planned_supply.py` 是「覆盖式写入」——
每次跑都把现有 csv 整个替换。本会话在干跑 `crawl_sz_land_deals.py
--pages 2 --page-size 20` 时发现：

- HEAD `sz_land_deals.csv` 有 **128 行 + 1 header = 129 行**（2020-2026 历史成交）
- 脚本 fresh 拉到 40 行（仅最近 2 页 × 20 行）
- 覆盖式写入后只剩 40 行 → **丢 89 行历史**

同款问题在 `sz_planned_supply.py`——脚本只 dedup **fresh 内**重复，
不读 existing。每次 cron 跑 `--max 4` 只抓最近 4 个公示，HEAD 之前 8 行（2022Q4-2025Q4）会丢历史。

### 修复

仿 `crawl_daily_wangqian.py:597-603` 的 merge-existing 模式：

- **`crawl_sz_land_deals.py`**：加 `read_existing()` + `merge_rows()`；
  按 `land_no` key merge（缺失 key 保留）；默认开启 merge、`--no-merge` 逃生口。
- **`crawl_sz_planned_supply.py`**：加 `read_existing()` + `merge_rows()`；
  按 `(year, quarter)` key merge；`read_existing` 把 year/quarter 转 int 避免
  sort 时 int/str 混排崩。
- 两脚本的 `merge_rows` 顺序策略：**existing 按 HEAD 顺序保留 + fresh new rows
  append 末尾**。避免 stable sort 引起的 28+/- 行 reorder noise。

### 验证

- `crawl_sz_land_deals.py --pages 2 --page-size 20` → `[merge] existing=128 fresh=40 merged=129`，git diff **+1 行 only**（B401-0151 福田 2026-08-11 真新数据）
- `crawl_sz_planned_supply.py --max 4` → `[merge] existing=8 fresh=4 merged=8`，git diff 空（4 个 key 全部命中现有）
- `npm run type-check`：PASS
- `npm test`：**145 文件 / 1205 tests** 全过（6.6s）

### 未做（按 memory 教训，等 cron 自然验证）

- 不在本地用 cron 实际跑（避免 idem potent 覆盖丢历史）
- 不动其它覆盖式写入的爬虫（crawl_gd_*.py 之类）——本次只针对丢历史最严重的两个
