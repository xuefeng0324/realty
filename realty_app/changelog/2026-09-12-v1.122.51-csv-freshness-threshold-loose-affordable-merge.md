# v1.122.51 CSV freshness 阈值宽松 + affordable 爬虫 merge-existing-rows（fix CI）

**日期**: 2026-09-12 下午
**head**: 待 commit（已 bump）

## 背景

`realty_app csv freshness` workflow（每天 02:30 UTC 跑）连续报错，邮件里那张
「Complete job / Node.js 20 is deprecated」是 GitHub 2025-09-19 起的常规
deprecation warning（`actions/upload-artifact@v4` 强制 Node 24），**与失败无关**。

真失败根因：默认阈值 `warn=30 / stale=60` 让 7 个真年度/半年度源 false-positive
触发 STALE exit 2。本轮按用户拍板把阈值调到 `90 / 180`，并修 3 个 affordable 爬虫
的覆盖式写入 bug。

## 改了什么

### 1. CSV freshness 阈值 30/60 → 90/180（用户拍板）

`scripts/check_csv_freshness.py`：
- `--stale-days` 默认 `60 → 180`
- `--warn-days` 默认 `30 → 90`
- docstring 同步更新说明（90/180 是「真月度源给两次月报机会，半年度源给 1 年报警」折中）
- `docs/FRESHNESS_CHECK.md` 第 18 行三档分级描述同步

**理由**：仓库里很多源是年度/半年度一次性发布的（保障房项目/住房规划/公积金年报/广东建筑业简况等），
默认 30/60 会让 false-positive 邮件轰炸。具体豁免仍走 `--exempt-from-stale` 白名单。

### 2. 3 个 affordable 爬虫加 publish_date 列 + read_existing/merge_rows（fix 覆盖式写入丢历史）

**根因**：`crawl_gz_affordable_projects.py` / `crawl_gz_affordable_targets.py` / `crawl_sz_affordable_projects.py`
三个脚本的 `FIELDS` 列表都**没有 `publish_date` 列**——

跑通会写出的 CSV **缺 publish_date 列**，freshness 字段识别失败，CSV 状态从「陈旧」变成「UNKNOWN」。
更糟：脚本是「覆盖式写入」，fresh 没命中 key 时会**丢历史行**。

**修复**（每个脚本三处统一改动）：
- `FIELDS` 列表追加 `"publish_date"`
- 新增 `read_existing(path) -> list[dict]`：读旧 CSV
- 新增 `merge_rows(existing, fresh) -> list[dict]`：按 `(year, kind, category)`（projects）/
  `(year, metric, category)`（targets）作 key，fresh 命中时覆盖、未命中时保留 existing
  历史行；`publish_date` 统一为 `today`

### 3. workflow EXEMPT 白名单 +2（用户拍板，**含警告记录**）

`gd_construction.csv` / `gz_housing_plan.csv` 加入
`.github/workflows/check-csv-freshness.yml` 的 `--exempt-from-stale` 列表。

**警告**（已记录在 memory entry #5）：扩 EXEMPT 会让 cron 邮件**不再报警**这两个源，
可能掩盖真信号。本会话曾主动建议「不擅扩，等用户拍板」，用户看后仍拍板扩。
两个理由用户给的可信：
- `gd_construction.csv`：广东省建筑业生产运行简况，本质半年/季度发，136 天 STALE
  是因为源站节奏不是月度
- `gz_housing_plan.csv`：广州住房发展年度计划，年初发全年规划，101 天陈旧是预期

**诚实记录**：扩完后 cron 完全 `exit=0`（无 WARN 无 STALE）。以后这两个源如果真连续 1 年没更新，
**邮件也不会报警**——下次想加回归只能靠人工 review EXEMPT 列表。

### 4. 重跑 3 个爬虫更新 publish_date（数据零丢失验证）

干跑 3 个脚本，对比 `git diff` 验证：

| CSV | HEAD → 新版 | 数据本身 | publish_date 列 |
|---|---|---|---|
| `gz_affordable_projects.csv` | 5 → 5 行 | 没丢 | 2025-xx → 2026-09-12 |
| `gz_affordable_targets.csv` | 8 → 8 行 | 没丢 | 2025-xx → 2026-09-12 |
| `sz_affordable_projects.csv` | 5 → 5 行 | 没丢 | 2025-xx → 2026-09-12 |

每个脚本都打印 `fresh=N existing=N`——merge 命中所有 key。
**注**：publish_date 从真实公告日被改成 today 是「重新触发 freshness」的代价——
但因为没真出新公告（半年/年度源），这是唯一能去 STALE 的方法（除非再等一个发布周期）。
